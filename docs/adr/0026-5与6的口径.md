# #5 与 #6 的口径：三分量多数票、消融对比量可配

两条指标的判据在自评里各偏了一次：

- **#5** 只看 token（"token 为主判据"）：实测 golden 相对 baseline 步数 −22.3%、耗时 +4.7%、
  token +1.5% → 判 fail，但"省步不省 token"其实说明 skill 有价值（少了乱走）。
- **#6** 的消融对比量写死 F1：human 型 skill 不跑 T2（ADR-0018），没有触发 F1，
  `ablation.py` 能生成消融副本却跑不出对比量 → 实证永远空。

决定：

1. #5 改**三分量多数票**：tokens / tool_calls / seconds 各一票（改善 > 0 即赞成），
   多数赞成 → pass，一票 → warn，零票 → fail；note 里逐个写出数值（不再只给一个数）。
2. #6 的 `ablation.json` 支持任意对比量：`{"metric": str, "full": num, "ablated": num,
   "higher_is_better": bool, "deleted": [...]}`；兼容旧形状 `f1_full`/`f1_ablated`。
   消融后变差（按 higher_is_better 判定）→ 被删段落必要（pass）；消融后更好 → 冗余（warn）。
   只有 `reason` 时保留评审面裁决并把原因附在 note 里（不静默丢）。
3. 判据变了就写进 note：报告读者要能看出"这次是按哪套口径判的"。

原因：为什么不是给三分量加权求和——权重是拍脑袋，且会把"省步"和"省 token"的语义差异抹平；
为什么 #6 不新造一个"消融对比量"字段名——`f1_full` 这种按指标命名的字段每换一个对比量就要改一次
schema，改成 metric/full/ablated 才是一次性结构。

## Consequences

- #5 的结论会随"哪两个分量改善"摆动：步数/耗时天然比 token 更容易改善，这是有意的（多数票）。
- #6 的消融在 human 型 skill 上要用 T3 的成本/质量分做对比量，需要额外跑一轮 golden（成本 ×候选段落数）。
- 改 `report.py` 即改评估器指纹（ADR-0010）：本次改动之前的报告 `comparable=false`。
