# 工作区复用与上传边界

旧上传每次解压到新的 `web/runs/uploads/<uid>`，同一份 skill 重复上传会产生多条路径；
用户也无法在页面上选择历史工作区。上传上限仍停在 70MB/200MB/3000 文件，和实际前端能力不符。

决定：

1. 上传先解压到临时目录，按被测 skill 内容 hash 落到 `web/workspaces/<slug>-<hash8>/skill/`；
   同一内容重复上传复用同一路径，内容变化新建工作区。
2. `workspace.json` 记录 `id`/`name`/`skill_sha256`/`source`/`created_at`/`last_used_at`；
   `GET /api/workspaces` 返回工作区列表，前端用下拉选择，不再提供本地路径输入。
3. 上传响应返回 `workspace_id`/`workspace`/`skill`/`evalset`/`skill_sha256`；评测集目录
   按 `evalsets/<name>/vN` 自动填，已有版本取最新，否则 v1。
4. 上传上限改为压缩包 1GB、解压 2GB、20000 个文件；路径穿越/绝对路径/符号链接仍拒绝。
5. `web/workspaces/` 是本地态，进 `.gitignore`；旧 `web/runs/uploads/` 保留只读，不迁移。

原因：为什么按内容 hash 而不是每次新建——路径稳定才能让运行历史、评测集和缓存归到同一
skill；为什么内容变化不覆盖——旧快照是历史报告可复现的前提；为什么移除本地路径——外部
用户不该为了评估去准备服务器路径，且本地路径绕过上传边界。代价：同一 skill 的不同内容会
留下多个工作区，需要后续按 `last_used_at` 清理。

## Consequences

- `reference.md` 的上传/API 段必须写工作区响应和 `GET /api/workspaces`。
- `web/index.html` 不再出现“本地路径优先”；上传后自动填评测集。
- 1GB 上传只改变 Web 入口，不改变 runner 的沙箱复制逻辑。
