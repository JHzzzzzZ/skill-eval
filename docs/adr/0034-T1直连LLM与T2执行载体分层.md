# T1 直连 LLM，T2+ 走可切换的执行载体

现在 T1 评审、触发判定、沙箱运行都直接调 pi CLI。T1 只需要一次无工具 LLM 调用，不该被
agent 框架绑架；T2+ 需要真实 agent 行为，载体要可切换（当前 pi，后续 Code Agent）。
ADR-0007 曾决定“没有第二个实现就不抽象”，现在 T1 直连 LLM 是第二个实现，Code Agent 是第三个，
抽象有了真实收益。

决定：

1. 新增 `llm` 层：OpenAI-compatible `/v1/chat/completions` 优先，薄适配器；Anthropic 后续补。
   T1 评审与触发判定走这一层，不经过 pi。
2. 新增 `harness` 层：接口 `run(prompt, cwd, model, ...) -> events/trace`；当前只实现 `pi`；
   `code_agent` 留接口不实现，前端只显示已实现项。
3. T2A/T2B/T3 的 skill 运行走 `harness`；T1 的 judge 走 `llm`。两者共享 config 的模型/端点，
   但不共享调用栈。
4. 证据格式：`llm` 调用留 request/response JSONL（含 model、prompt hash、耗时）；
   `harness` 继续留 pi 事件流。
5. 凭据：config 写 `api_key_env`（已存在的变量名）或前端一次性输入，不新增环境变量；
   密钥不落报告、不落 results。

原因：为什么不继续用 pi 跑 T1——pi 是 agent 框架，会带入工具、会话、系统提示，ADR-0022 要求
评审无工具，直连才能从结构上保证；为什么不在 T2+ 也直连——T2+ 测的是 skill 在真实 agent 里的
行为，直连 LLM 测不到工具调用与加载路径；为什么现在才抽象——有 T1 直连与 Code Agent 两个真实
实现，不再是空想抽象。代价：两套调用栈、两份证据格式；`llm` adapter 必须自己保证“无工具”，
不能靠 `--no-tools` 开关。

## Considered Options

- 继续全部走 pi：改动最小，但 T1 的“不依赖 agent 框架”无法成立。
- 只做 Anthropic Messages：当前 pi 的模型配置多为 OpenAI-compatible，先做 OpenAI 覆盖面更大。

## Consequences

- `judge_runner.py` / `trigger_judge.py` 从“拼 pi 命令”改成“调 llm adapter”；原始证据路径改。
- `trace_run.py` 的 pi 专有逻辑收进 `harness/pi.py`，事件聚合仍复用 `EventAggregator`。
- 改这两层即改评估器指纹（ADR-0010）：之前的历史报告全部 `comparable=false`。
