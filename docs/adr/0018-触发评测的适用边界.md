# 触发评测的适用边界与加载判定

自评 `skill-evaluator` 自己时（results/auto-0f14b3b）跑了 4 条触发探针，暴露三处载体缺陷：
3 条读到 SKILL.md 的 run 一次都没早停（agent 普遍写 `cd <skill目录> && cat SKILL.md`，而判定
只做绝对路径子串）；被测 skill 声明 `disable-model-invocation: true` 时，pi 会把该 skill 从系统
提示里滤除（实测 `--skill` 加载后模型答"无 available_skills 段"），"按 description 触发"结构上
不可能；4 条并发 run 共用一个 worktree，一条 run 写的 `scratch/scan_all.py` 被另一条当成仓库内容分析。

决定：

1. early-exit 判定改**路径解析**：args 里每个 token 解析到 `<skill目录>/SKILL.md` 即命中——相对路径
   按同一条命令里最近的 `cd` 目标解析，否则按运行 cwd（`trace_run` 把 worktree 传给 `EventAggregator`）。
   只报文件名、不带目录成分的 token 要求同一条命令里有读取动词（`find . -name SKILL.md` 不算加载）。
2. `#7 resolved=human`（即 `disable-model-invocation: true`）时 **T2 整档不跑**：`#1` 记 `skipped`
   并在报告里注明理由；已实测的数据原样留在 `data` 里作证据，但不改判。
3. 每次 run 前重置工作树（`git -C <worktree> clean -fdx`，或每个 run 单独 `git worktree add`）；
   并发 run 必须各自独立 worktree。

原因：为什么不是"照跑完再人工剔除噪声"——4 条探针 0 次早停，单条白跑 85~358s / 3.7 万~9.4 万 token，
30 条的 T2 就是纯烧钱，且跑出来的 P/R 混的是 cwd 探索与显式路径，不是 description 的触发能力；
为什么要求读取动词——只把"相对路径也算命中"放宽会让 `find`/`grep -l` 这类只列名字的命令把
should-not 误杀成 triggered（ADR-0007 当初修的就是这类假阴性）。

## Considered Options

- 上 shell 解析器（bashlex 之类）还原每条 bash 命令的真实 cwd：多一个第三方依赖、Windows 上装不动。
- 要求被测 run 一律写绝对路径：靠 agent 自觉，不可控，实测它就是不这么写。

## Consequences

- 判定变宽 → 会更早停：截断 run 的回答为空，触发裁决继续由 `trigger_judge.py`（LLM）兜底，
  early-exit 只影响成本与 trace 截断（口径已写在 reference.md § 运行场景）。
- `resolved=human` 的 skill 少一次体检：#1 不再有分数，只能靠静态面确认 frontmatter 声明的调用方式。
- 改 `trace_run.py` 即改评估器指纹（ADR-0010）：本次改动之前的报告全部 `comparable=false`。
