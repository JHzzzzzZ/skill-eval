# 真实输入多 case 与无标签评估

T2B 原设计只接收一例真实输入，且只比较 token/步数/耗时；用户无法一次提交多条业务输入，
没有标签时也没有可解释的质量结论。

决定：

1. 真实输入改为多条：前端动态增删填空，`prompt` 必填；`expect` 选填（验收标准）；
   `note` 选填（仅显示）。后端自动编号 `c001` 起，不要求用户输入 ID 或 JSON。
2. 同时支持 `.jsonl` 导入；一行一条，只有 `prompt` 必填，`note`/`expect` 可选。
   前端导入后仍以卡片展示，可继续编辑；单次最多 20 条。
3. 每条跑 golden（加载 skill）与 baseline（不加载）两臂；逐条落 `t2b/cases/<id>/`，
   失败/超时的 case 跳过，不记 0。
4. 有 `expect`：用 `compare.py` 判断实际输出是否满足验收标准，汇总匹配率；不把自由文本
   当字符串精确匹配。
5. 无 `expect`：做双向 A/B 盲评（交换左右各一次），两次一致才算胜，否则平局；汇总偏好
   胜率，**不称 accuracy**。没有标签也不做“标准答案”推断。
6. `#11` 的必要性裁决仍由成本三分量决定；匹配率/偏好胜率作为同一指标的辅助证据展示，
   不合成加权总分。

原因：为什么不让用户写 JSON——动态表单降低输入门槛，ID 由后端生成避免重复和缺号；
为什么无标签不硬判对错——没有验收标准时只能比较相对偏好，伪装成 accuracy 会误导；
为什么双向盲评——单次评审有位置偏差，交换顺序能暴露不一致；代价是每条多两次评审调用，
20 条时成本明显增加。

## Consequences

- T2B 进度必须逐条打印 `有 skill`/`无 skill` 两臂，不能只报阶段开始/结束。
- 报告分开显示“有标签匹配率”和“无标签偏好胜率”，并写明样本数。
- 真实输入仍只存本地 `uploads/`，报告不回显正文。
