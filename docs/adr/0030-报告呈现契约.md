# 报告呈现契约：表格优先 + 原始 JSON 折叠 + 闸门可见 + 建议与指标同源

报告页有三处结构性缺陷：19 条指标只有 4 条有定制表，其余是裸 `<pre>` 原始 JSON；可移植性闸门（`static.json.hardcoded`，ADR-0008）`report.py` 从未读取，
导致"整体 fail"在页面上一个红字都没有（`conclusion()` 只看 19 条指标裁决）；而 `reference.md` 声称的"每条指标一节：分数/证据/建议"里，"建议"从未实现——
建议只活在评估会话的对话里，与指标裁决可以互相矛盾而无人发现。

决定：

1. **表格优先**：所有指标 data 一律表格化——已知形状走定制表（#1/#5/#6/#8/#10/#13/#14 + 原有的 #4/#9/#12/#15），其余走**通用兜底**（dict/list 递归压平成 key-value 表）。
2. **原始 JSON 一律保留，有表就折叠**（不管多短），无表且短才内联；HTML 不得比 md/json 少信息。
3. **闸门可见**：`hardcoded` 非空 → #13 裁决 = fail（ADR-0015 已把闸门归到 #13）；`stale_refs`、
   `scan_excluded_dirs` 作为 #13 卡的信息行（不改裁决）。
4. **建议内联 + 汇总页**：`report.json` 顶层新增 `advice` 数组，每项 `{metric, severity, problem, evidence, action}`，由 `build()` 从裁决确定性派生；指标卡下方内联该指标建议，`report.html` 另有「优化建议」tab（按严重度排序、带 `#N` 锚点跳回指标卡），report.md 加 `## 优化建议` 段。
5. **结果符号统一**：pass=✓、fail=✗、warn=⚠、skipped=–；用于卡片徽章、表格结果列，并新增 19 行总览表。

原因：为什么建议不由 LLM 生成——建议与裁决同源才谈得上"强对应"，LLM 生成的建议会与指标脱钩（正是本次要修的问题），且每次渲染花 token、产生抖动。
为什么 `advice` 进 `report.json` 而不是只在渲染层算——三份产物（json/md/html）吃同一个源，md 与 html 不会漂。为什么不新增第 20 条指标承载闸门——ADR-0004 固定 19 条。

## Considered Options

- 建议单独一个 HTML 页面、不内联到指标卡：读的人要在两处对照，"这条建议对应哪个问题"仍靠人脑维护。
- 只做折叠、不加表格：折叠后的原始 JSON 仍需人肉解析，19 条指标里 10 条如此。

## Consequences

- `report.json` 多一个顶层 key（19 条指标的 key 数不变）。
- #13 裁决口径变严：历史报告中带绝对路径的 skill 会从 pass 翻 fail（修 bug，不是口径漂移）。
- 通用兜底表对深层嵌套 dict 会压平成长表（如 #12 的 model_robust 子树）——信息不丢，可读性靠定制表。
- 未测（skipped）指标的 `action` 是"补测"而非"修问题"：未测是缺口不是问题，给错方子等于建议与问题脱钩。
