# LLM 评审的调用口径：单发固定 prompt，温度不可控

`reference.md` 原本声明 LLM 评审是 "temperature=0、单次"，但 pi CLI 没有 `--temperature`/`--seed`
参数，`_subprocess.build_mode_args` 只传 `--model`/`--thinking`——契约写了一条执行不了的要求。实测：
同一个固定 prompt 重复 4 次逐项一致（#16、#6 各 4/4 同分），而把同一 rubric 交给"已探索过被测仓库、
带着上下文"的编排 agent 去判，同一份内容得出不同结论（#16 1.0 vs 0.5，#6 0.5 vs 0.75）——
偏差的主要来源不是采样随机性，而是 prompt 的来源。

决定：

1. 评审调用一律**独立单发**：固定 prompt = rubric 全文 + 被测文件（+ rubric 自声明的附属文件），
   不携带编排 agent 的历史或探索结论。要重放就照这条拼 prompt。
2. 删掉 "temperature=0" 的说法，改成三条可执行的：同 prompt、单发、留原始事件流
   （`raw/judge-events/<metric>.events.jsonl`）。
3. 需要更高可信度时开 `JUDGE_SAMPLES=3`：同一 prompt 跑 3 次，逐项取中位数（成本 ×3，口径写进报告）。
4. 多模型交叉仍留给后续（现由 ADR-0011 的跨模型一致率覆盖 #12，不覆盖评审）。

原因：为什么不改成"直接调 provider API 传 temperature=0"——评估器只有一条 LLM 通路（pi CLI
子进程，ADR-0007），为评审再开第二条通路就等于承认两条通路可以给出不同证据；为什么不是只上
N=3——三倍成本压不住"prompt 不同源"这个更大的偏差源，先固定 prompt 更便宜也更有效。

## Consequences

- 检查点少的 rubric（#16 只有 2 项）单项翻转就是 ±0.5 分：评分粒度受 rubric 设计限制，
  想稳就得把检查点拆细，而不是靠多跑几次。
- `raw/judge-events/` 会让 results 目录变大（每条评审一次完整事件流），换的是裁决可回看。
- 改 `reference.md`/`judges/*.md`/`scripts/*.py` 即改评估器指纹（ADR-0010）：本次改动之前的
  报告全部 `comparable=false`。
