# 依赖全面性进静态面（#8 的第三源）

#8 一直是两源：trace 报错（沙箱面）+ `judges/deps.md` 语义评审。两源都测不出"实际用了什么 vs 声明了什么"——
无报错且无评审输出时 #8 直接 pass；`find_stale_refs` 只查反向（声明了但包内不存在）。实测缺口：一个 skill
用 git、pi、python，文档里一个依赖都没声明，仍然 pass。用户侧的同一观察：最小依赖这一项没有对依赖**全面性**的检查。

决定：

1. `static_check.py` 新增三个字段——`deps_used`（shebang 解释器、python `import` 的非标准库非本地模块、
   `subprocess` 调用里字面量 argv[0]）、`deps_declared`（SKILL.md 正文 + reference.md + `requirements.txt`
   + `check-deps.sh` 里出现过的名字）、`deps_missing`（差集）。
2. `report.py` 把 `deps_missing` 作为 #8 的**辅证**：非空 → #8 至少降为 warn，不 fail。
3. `judges/deps.md` 加第 4 检查点"声明清单完整（与脚本实际用到的一致）"。

原因：为什么不判 fail——缺声明不影响运行，fail 会与 trace 面"跑得通"的证据打架，也会让 #8 变成文档格式审查。
为什么不全靠评审——"用了什么"是可数的静态事实（ADR-0017 的同一原则），且评审要花 LLM 调用、评审缺失时该缺口完全无人看。
为什么声明面取四者并集——单一来源都会漏：`requirements.txt` 只覆盖 python 包，`check-deps.sh` 只覆盖硬依赖，只有文档正文才会写"需要 pi CLI"。

## Considered Options

- 解析 `subprocess` 的完整 argv 并逐个查命令：实测 argv 常由变量组装（`[sys.executable, str(SCRIPT)]`），
  能静态取出的只有字面量首参，做全量解析的收益是假象。
- 把缺失声明报成 error、让 `passed=false`：会把"文档没写全"升级成"包不可用"，与闸门语义（ADR-0008）混淆。

## Consequences

- 声明面 = 四份文件里出现过的**任意词**（包括正文随口提到的），比"声明清单"宽——偏漏报方向；
  同义词（"Python3" vs "python"）同样漏判。已知局限写进 `reference.md`，不在代码里堆同义词表。
  宁可漏报，不要用启发式制造假 fail。
- `static.json` 契约新增三个字段；历史 `static.json` 缺字段时 #8 行为不变（老产物照旧两源裁决）。
