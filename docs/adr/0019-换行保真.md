# 换行保真：副本与 worktree 必须与存档字节一致

Windows 上 `core.autocrlf=true`（实测机器默认）时，被测 skill 的只读存档 51 个文件里 15 个
（`judges/*.md`、`scripts/_console.py`、`scripts/_subprocess.py`、`tests/*`）在副本
`git init + add + commit` 与 `git worktree add` 之后被重写成 CRLF——同一份上传得到两个
`content_sha256`（`2b69cdc3…` vs `3249fa12…`），`skill_fingerprint` 认不出"评的是哪份内容"。

决定：

1. 副本 repo 的创建顺序固定为：`git init` → **`git config core.autocrlf false`** → `git add -A`
   → `git commit` → `git worktree add`（worktree 继承副本的本地 config）。
2. 存档用**字节拷贝**进副本（`tar -cf - -C <存档> . | tar -xf - -C <副本>`），不经过 `git clone`
   或会做换行转换的复制工具。
3. 副本里**不写 `.gitattributes`**：副本必须等于上传内容，多一个文件就改变了被测对象与指纹。
4. 收尾校验：存档 vs worktree 逐文件比字节，必须 0 处不同（修复前为 15 处）。

原因：ADR-0003/0010 的 `content_sha256` 是"单看 results 目录就知道评的是哪份 skill"的唯一来源，
字节不一致时它退化成一个随机数；为什么不去改宿主机全局 `core.autocrlf` 或给被测仓库加
`.gitattributes`——那是用户环境与用户仓库的配置，评估器只能在自己的副本里关转换（ADR-0008 的
边界：不改用户环境、不写死机器假设）。

## Consequences

- 副本内不再"统一 LF"：CRLF 文件保持 CRLF、LF 保持 LF，指纹稳定性优先于风格统一。
- 跨平台搬同一仓库（Windows 存档 → Linux 评估）仍可能有换行差异：指纹只在同一份存档内部可比，
  跨版本对比仍以"存档字节"为准（ADR-0010 的 `comparable` 语义不变）。
