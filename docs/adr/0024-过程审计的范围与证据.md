# 过程审计的范围与证据（#10）

自评 T3 时 #10 判了 fail，理由里写着"从未推进到评测集/触发/评审/报告任一后续步骤"——而同一条 trace
的产物证明报告已产出（沙箱内 `evalsets/wrap-up/results/auto-28c05da/report.md`），且用例本身就限定
"只跑 T0"。判官拿不到用例范围，只能对着完整 9 步流程判，于是把"用例没要求的事没做"记成了无意义步骤。

决定：

1. `process.py` 增 `--case <用例.json>`：把用例的 prompt 与 expect 写进审计 prompt，并明确
   "用例没要求的步骤不算无意义"；不给 `--case` 时退回旧行为（只对照声明流程）。
2. `step.args` 的保留上限从 200 提到 2000，截断时写 `args_truncated: true`。
   **更正**：原判据说"200 字符把 report.py 长命令切断"——实测不成立：pi 的 bash/read 工具
   `args` 是 dict（`{"command": ...}`），旧代码的截断分支只作用于字符串形态，对它们从未生效
   （golden trace 里 521 字符的命令完整保留）。上限仍然提高，是为了字符串形态的工具参数。
3. 报告里的 #10 结论必须与 #9（expect vs actual）交叉看：两者对同一条 run 给出相反结论时，
   先在报告里写明分歧，而不是直接采信其中一方。

原因：为什么不是让判官自己猜用例范围——trace 里没有原始 prompt（trace_run 不存 prompt），
猜出来的范围无法复核；为什么保留 `--case` 可选而不是强制——旧调用方（离线重算/历史 trace）
没有用例文件，强制会让它们全部失败。

## Consequences

- 过程审计的结论从此依赖"调用方传没传 --case"：报告 `data` 里会带 `case_scope` 字段说明本次口径。
- #10 与 #9 的分歧成为常态而非异常：两者测的是不同东西（步骤合理性 vs 产出匹配度），
  报告要能同时容纳"过程很绕但产出正确"。
- 改 `process.py`/`trace_run.py` 即改评估器指纹（ADR-0010）：本次改动之前的报告 `comparable=false`。
