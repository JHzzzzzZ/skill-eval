# 阶段级检查点与停止后的局部报告

评估跑到一半停止时，旧实现只杀进程，不写报告；逐 rubric / 逐 case 落缓存又会把半截结果当成可复用进度，恢复语义复杂且容易误判。

决定：

1. 检查点只放在阶段边界：T0 完成、T1 七个 rubric 全齐、T2A/T2B/T3 各自产物完整时才写缓存；半截阶段不写、不续跑，下次整档重跑。
2. 停止时按产物判定最高完整阶段，只用该阶段及之前的指标生成局部报告；当前半截阶段的数据不参与结论。
3. 局部报告写 `partial: true` / `completed_stages` / `stopped_at`，页面顶部标注“仅展示已完成阶段”；连 T0 都没完成不生成空报告。
4. 局部报告停在 T0 时不读 T1 的评审（包括 `pii` / `brevity`），避免未完成阶段把 T0 指标拉低。

原因：逐 case 检查点看似省时间，但恢复时要区分“跑完”“跑了一半”“产物合法”，还会让报告与缓存出现两套完成语义；阶段边界是现有 runner 和缓存 key 已经存在的天然分界，重跑成本可接受。停止后直接出完整报告会把半截数据冒充结论；完全不出报告又浪费已完成的 T0/T1。局部报告把“已完成”与“未完成”显式分开，代价是当前阶段要整档重跑。

## Consequences

- 停在 T1 中间会丢掉该档已完成的 rubric，下次重跑 T1；T2A/T2B/T3 同理。
- 局部报告的指标数少于完整报告，不能用于跨版本完整对比。
- `report.py` 与前端必须同时识别 `partial`，否则页面会把局部报告显示成完整结论。
