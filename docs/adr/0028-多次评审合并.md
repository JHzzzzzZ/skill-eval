# 多次单发评审的合并（JUDGE_SAMPLES 落地）

ADR-0020 把"temperature=0"改成"固定单发 prompt + 留事件流"，并把 `JUDGE_SAMPLES=3` 写进
可配参数——但 `judge_runner.py` 只做校验，没有任何地方做多次评审的合并，那个选项一直是空头支票。
同一次自评里也确实撞到过口径差：带上下文的一次判 #16=0.5，固定 prompt 判 1.0。

决定：

1. `judge_runner.py` 增 `--merge <a.json> <b.json> [...] [--out f]`：逐项**多数票**
   （3 次取 2 即通过；2 次平票算不通过，保守），`score` 仍按 `pass 项数/总项数` 推导（#5 口径不变）。
2. 合并输出保留证据：`samples`、`per_sample_scores`、`disagreements`（票型）、
   以及未通过项的原文引用（`evidence` 必须非空，否则校验器会拒）。
3. 缺席项按"未投票"处理（只统计实际出现过的票）；样本本身不合法（过不了 `--validate`）即整体拒绝，
   不静默跳过——宁可没有结果，不要用坏样本凑数。

原因：为什么不是取中位数——item 的 `pass` 是布尔，三次投票的中位数就是多数票，措辞换成
"中位数"只会让人以为分数是连续的；为什么合并放在 judge_runner 而不是新脚本——
它已经是评审输出的唯一门禁（校验 + 合并同一处契约），多一个脚本就多一处要同步的契约。

## Considered Options

- 3 次全过才算过（更严）：会把"2 次说对 1 次说错"的项直接判死，比多数票更容易被单次噪声劫持。
- 把 3 次输出都塞进报告：`judges/<metric>.json` 只允许一份，多份会让 report.py 的选择变成隐式规则。

## Consequences

- `JUDGE_SAMPLES=3` 现在是可执行的：跑 3 次 → `--merge` → 落 `judges/<metric>.json`；成本 ×3。
- 多数票会掩盖"某次评审整体跑偏"：所以 `disagreements` 与 `per_sample_scores` 必须一起看。
- 改 `judge_runner.py` 即改评估器指纹（ADR-0010）：本次改动之前的报告 `comparable=false`。
