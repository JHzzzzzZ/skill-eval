# 五档评估档位（T0–T4）

评估全量一次 ~1h，其中确定性脚本只占 0.75s，沙箱运行占大头（串行等价 1789s），评测集人工审核曾造成 ~22min 纯等待（timing-analysis，auto-b9d7fab）。据此把评估分为增量递进的五档：T0 static（~1s）/ T1 review（~3min）/ T2 trigger（~10min，**默认**）/ T3 core（~25min）/ T4 full（~1h），入口 `--tier`，高档复用低档产物（按被测 skill 的 content_sha256 判定，不一致作废重跑）。切分线对应真实等待成本：想快的人停在 T1（12/19 指标，不碰沙箱），skill 迭代中测触发措辞用 T2，定版才跑 T4。

## Considered Options

- **三档（静态/快速/全量）**：被否——"只测触发"是真实需求（迭代中最常改的就是 description/触发措辞），砍掉 T2 会迫使这类评估跑主运行。
- **默认 T3**：被否——评估器的高频用法是迭代中快速看触发精准度与评审分，T2 已下结论；T3/T4 显式要才跑。
- **重复×N 留 T4**：被否——数据上只多 ~4min，挪进 T3 让常规验收就带幂等/稳定性结论。

## Consequences

- 低档先行、后续**增量补跑（staged）**是正常路径，不再是故障处置；沙箱失败退档才叫**降级（fallback）**，两词在文档中不再混用。
- 评测集审核从人工硬门禁改为 LLM 自动审核即冻结（`reviewed_by: "ai"`，不阻塞后续档位），审核模型必须与生成阶段不同源（`--review-model` / `SKILL_EVAL_REVIEW_MODEL` / 首次运行交互选择）；人工复核后可把 `reviewed_by` 升级覆写为 `"human"`，不回滚。报告对 AI 审核口径显式标注。
- report.json 增加 `tier` 字段；#14 evolution 跨版本 diff 时先比 tier 再比分数，档位不同不直接比指标值。
