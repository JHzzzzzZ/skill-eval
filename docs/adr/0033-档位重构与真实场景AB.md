# 档位重构为 T0/T1/T2A/T2B/T3

原五档把触发评测（T2）与核心沙箱（T3）分开，但必要性 A/B 与最小依赖仍埋在 T3，且 T4 不开放。
用户要求精准触发走 T2A + early-exit，必要性 A/B 与最小依赖走 T2B，并要求 T2B 用一例真实输入
触发真实业务场景。

决定：

1. 档位改为 T0 静态 / T1 LLM 评审 / T2A 触发评测 / T2B 真实场景 A/B / T3 核心沙箱。
2. T2A：三组触发 prompt 带 `--early-exit`；human 型整档跳过，新 #10（旧 #1）记 skipped。
3. T2B：用户提供 ≥1 例真实输入；同 cwd、同输入跑 golden（加载 skill）与 baseline（不加载）
   两臂；新 #11（旧 #5）必要性、新 #12（旧 #8）最小依赖从这两臂裁决。未提供输入 → 整档
   skipped；不自动生成“真实”输入。
4. 新 #11 报告样本数 n；n<3 时最高 warn 并注明“样本不足”，不因 n 小直接 fail。
   真实输入存 `uploads/`（已 gitignore），报告只回显哈希 + 标签。
5. T3 继续用冻结 cases 跑 #13 成本 / #14 结果可验证 / #15 稳定性 / #16 幂等；
   不与 T2B 的真实输入混用。
6. T4 不开放；其指标已按 ADR-0032 删除。

原因：为什么把 #11/#12 前移——它们只需要“有/无 skill”两臂，不需要完整核心沙箱，放在 T2B
能让用户在十分钟内看到 skill 是否值得加载；为什么要求真实输入——冻结 cases 是合成场景，
必要性结论容易“跑得通但业务没用”；为什么 n<3 只给 warn——一例能证明可用，不能证明统计显著，
报告必须把这一点写明，而不是装作有结论。代价：T2B 与 T3 各跑一次 golden，成本增加；
真实输入可能含敏感信息，只能留在本地 `uploads/`。

## Considered Options

- T2B 复用冻结 cases：省一次运行，但“真实业务场景”的要求落空。
- 一例也允许 pass：报告更乐观，但统计上站不住。

## Consequences

- `reference.md` 档位表、`SKILL.md` 第 4/5/6 步、`report.py` 的 `tier` 字段全部改。
- 报告要能显示“n=1，样本不足”，不能只给一个三分量结论。
- T2B 的 golden trace 与 T3 的 golden trace 是两份产物，不能互相冒充。
