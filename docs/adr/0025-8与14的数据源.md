# #8 与 #14 的数据源：多 trace 并集、依赖信号分类、evolution.json

两条指标的数据源在自评里都出了问题：

- **#8** 只读单条 `golden.json`：本次取 c1-r1（无依赖类报错）→ pass；同一 case 的 r3 里有
  `cat: AGENTS.md: No such file or directory`（agent 自己写错相对路径），换成那条就会被判成缺依赖。
- **#14** 在 `report.py` 里硬编码 `skipped`（"evolution.py 独立产出"），没有任何分支能给
  pass/warn/fail —— 指标表说它已实现，报告里却永远不参与结论。

决定：

1. #8 的数据源扩为**全部** `traces/golden-*.json`（存在即用），否则退回单条 `golden.json`；
   `data.sources` 记录纳入了几条。
2. #8 的依赖信号分两档：强信号（`command not found` / `ModuleNotFoundError` / `not installed`…）
   直接算；弱信号（`no such file` / `not found` / `不存在`）要求报错里带**含分隔符的路径**才算
   （`bash: scripts/check-deps.sh: No such file` 算，`cat: AGENTS.md: …` 不算）。
   不算的进 `ignored_errors`，保留可见（不静默丢）。
3. #14 读同目录的 `evolution.json`（`evolution.py --out` 落盘）：`comparable=true` → pass，
   `false` → warn（差异不构成回归证据）；没有该文件才 `skipped`。

原因：为什么不在 #8 里"只统计前几步的报错"——步序不代表阶段，agent 的探索顺序不固定；
为什么 #14 不直接调 evolution.py——report.py 不 subprocess 调脚本（ADR-0006 的分工），
产物文件才是接缝。

## Consequences

- #8 变严：任一条重复运行里有真实依赖报错就 fail（并集语义），这是想要的方向——环境问题不该被
  一次"幸运的干净 run"掩盖。
- #14 从"永远 skipped"变成可裁决，历史报告里它的 `skipped` 不再可比（评估器指纹已变）。
- 改 `report.py` 即改评估器指纹（ADR-0010）：本次改动之前的报告 `comparable=false`。
