# #16 rubric 拆细，并允许核对被指向的自检脚本

#16 原本只有 2 个检查点（校验置前 / 覆盖完整），按 ADR-0020 的计分公式，单项翻转就是 ±0.5 分；
>实测同一条 rubric 两次判定给出 1.0 与 0.5 —— 差异不在采样随机性，而在"覆盖完整"这一项本身没有可
判定的口径（判官只能自行决定算不算完整）。自评还发现 6 条 rubric 的输出模板里残留历史笔误
（`score=2 时可为空数组`，而 #5 契约没有 2 分档），模板坏形状没人拦。

决定：

1. `judges/precheck.md` 拆成 6 项：校验可照做 / 校验置前 / 依赖覆盖完整 / **声明与实现一致** /
   失败处置明确 / 分级正确。单项权重从 0.5 降到 0.17。
2. 新增"声明与实现一致"一项：正文对自检覆盖面的描述不得超出脚本实际检查的范围——脚本查什么，
   正文说什么（覆盖完整看依赖是否漏，声明一致看承诺是否虚高，两件事分开判）。
3. rubric 声明的评审输入一并喂给判官：`precheck` 的输入 = SKILL.md（含 frontmatter）+ 它指向的
   自检脚本内容。"覆盖完整"只能对着脚本判，不给脚本等于让判官猜。
4. 修正 6 条 rubric 的 `score=2` 笔误，并加结构测试：每条 rubric 必须给出合法 JSON 模板、
   score 公式、≥2 个检查点，且不残留 `score=2`。

原因：为什么不是只加检查点数量——加分项不改口径，判官照样各判各的；为什么"声明与实现一致"单独成项——
它和"覆盖完整"的失败方向相反（漏依赖 vs 虚报覆盖），合并会让一条 fail 掩盖另一条；为什么模板也要测——
rubric 是判官的输入契约，模板不可解析时主 agent 只能照抄坏形状。

## Considered Options

- 保持 2 项、靠 `JUDGE_SAMPLES=3` 取中位数压抖动：3 次都判不准同一件模糊事，中位数还是模糊。
- 把 #16 完全交给静态面（脚本检查脚本）：自检脚本的覆盖面是"声明 vs 实现"的语义判断，静态面判不了。

## Consequences

- 改 `judges/*.md` 即改评估器指纹（ADR-0010）：本次改动之前的报告全部 `comparable=false`。
- #16 的评分粒度由 rubric 项数决定，项数一改，历史分数的可比性只在同一 rubric 版本内成立
  （跨版本比 #16 分数前先看评估器指纹）。
- "声明与实现一致"会让"正文写得比脚本全"的 skill 掉分：要么补脚本，要么把正文改成与脚本一致。
